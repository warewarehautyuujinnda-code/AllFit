## 1. 背景と目的

現在FitLogは、体重・筋トレ・ラン・食事の4記録を蓄積するアプリである。要件定義書のロードマップ（フェーズ3）では「蓄積データのAI分析」が構想されていたが、これをさらに一歩進め、以下のループを継続的に回せるようにする。

1. 長期目標を決める
2. 長期目標をもとに、AIと相談しながら具体的な一週間の計画（週次計画）を立てる
3. その週、既存の記録機能で実績を記録する（変更なし）
4. 週末〜週初に、計画と実績を比較する
5. その比較結果を踏まえて、AIと相談しながら次週の計画を立てる（2に戻る）

この設計書は、上記ループのうち「FitLogアプリ側で何を持ち、何を表示するか」と「計画データをどうやってアプリに反映するか」を定義する。AIとの相談自体（対話）はアプリの外（Claude Codeなど）で行うため、本設計のスコープには含まない。

## 2. スコープ

### 2.1 今回作るもの

- Room新規テーブル: `GoalEntity`（長期目標）, `WeeklyPlanEntity`（週次計画ヘッダー）, `WeeklyStrengthTargetEntity`（週次の筋トレ種目別目標）
- アプリ起動時のシード同期処理（コード内に持たせた計画データを、追記専用でRoomに取り込む）
- ホーム画面「今週の目標」セクション（筋トレ・ラン・体重の状況＋長期目標の表示）
- 筋トレの種目ピッカー画面・セット入力画面への、今週の計画の目印表示
- ランニングのメイン画面への、今週の残り目標distanceの表示
- 新スキル `/weekly-plan`（仮称）: kaizenと対になる、計画データ更新専用のGitワークフロー
- 達成率計算ロジックのユニットテスト

### 2.2 対象外（今回は作らない）

- アプリ内での目標・計画の作成/編集UI（入力フォーム）。計画の作成・更新は常にGit経由。
- AIとの対話をアプリ内に組み込むこと（チャットUI、LLM APIの直接呼び出し等）。対話はアプリの外で行う前提。
- 食事（カロリー・PFC）に対する週次目標。
- 体重の週次目標。**体重の目標は既存の `WeightGoalStore` をそのまま利用する**（下記§4.4）。
- 長期目標（GoalEntity）の自動達成判定。自由記述のため、達成したかどうかの自動判定はしない。テキストとして表示するのみ。
- 計画の詳細画面（タップ遷移する専用ビュー）。ホームのセクションと各タブの目印表示で完結させる。
- 複数の長期目標を切り替えるUI。データ上は複数件持てるが、表示は「直近1件」のみを前提とする。
- 筋トレ目標（種目・reps・sets）の自動厳密判定。「実施したかどうか」のみを判定し、reps/setsは目安表示に留める（§8参照）。

## 3. 全体アーキテクチャ

**原則: FitLogアプリ本体は表示専用。計画データの書き込み経路はGit経由のみ。**

```
[Claude Codeでの計画会話]  … 週次実績の確認 → 相談 → 次週の数値目標を決定
        ↓ /weekly-plan スキル
[ブランチ作成 → PlanSeeds.kt に追記 → ビルド確認 → PR作成]
        ↓ 人間がレビューしてマージ（mainは常に安全な状態を保つ）
[ユーザーが最新版をビルド・インストール]
        ↓ アプリ起動時
[PlanSeeds の内容を Room に同期（追記のみ、上書きなし）]
        ↓
[ホーム画面・筋トレ/ランタブが、既存4テーブルの実績と新3テーブルの計画を
 その場で突き合わせて達成状況を計算・表示]
```

kaizenスキルとの対応関係:

| | kaizen | /weekly-plan |
|---|---|---|
| 対象 | 機能の不満・バグ | 目標値・週次計画 |
| 起点 | フィードバック | 実績確認＋AIとの相談 |
| 変更内容 | コード修正 | `PlanSeeds.kt` への追記 |
| 成果物 | レビュー待ちPR | レビュー待ちPR |
| マージ | 常に人間 | 常に人間 |

## 4. データモデル

既存テーブル（weight/strength/strength_set/running/meal等）は無改造。以下を追加する。

### 4.1 GoalEntity（長期目標）

| 項目 | 型 | 必須 | 説明 |
|---|---|---|---|
| id | 文字列 | ○ | 一意のID |
| title | 文字列 | ○ | 自由記述（例: 「2027年3月までにハーフマラソン完走」） |
| targetDate | 日付 | | 目標日。任意 |
| createdAt | 日付 | ○ | 作成日 |

複数件保持可能。UI表示は `createdAt` が最も新しい1件を「現在の目標」として扱う。自動達成判定はしない（自由記述のため）。**体重の目標はここに含めない**（§4.4）。

### 4.2 WeeklyPlanEntity（週次計画ヘッダー）

| 項目 | 型 | 必須 | 説明 |
|---|---|---|---|
| id | 文字列 | ○ | 一意のID |
| weekStart | 日付 | ○ | その週の開始日（月曜始まりを仮定。§11参照） |
| goalId | 文字列 | | 紐づく長期目標のID。任意（表示上は使わないが、AIとの相談履歴として残す） |
| targetRunningKm | 数値 | | その週のラン合計距離目標(km)。任意 |
| memo | 文字列 | | AIとの相談で決めた補足。任意 |

### 4.3 WeeklyStrengthTargetEntity（週次の筋トレ種目別目標）

| 項目 | 型 | 必須 | 説明 |
|---|---|---|---|
| id | 文字列 | ○ | 一意のID |
| weekPlanId | 文字列 | ○ | `WeeklyPlanEntity.id` への参照 |
| exerciseName | 文字列 | ○ | 種目名（`ExerciseCatalog`のプリセットに無い自由入力も可） |
| targetReps | 数値 | | 目標回数の目安。任意 |
| targetSets | 数値 | | 目標セット数の目安。任意 |

1つの週次計画に対し、複数の種目目標を持てる。

### 4.4 体重の目標（既存機能を流用）

体重の長期目標は、既に `WeightGoalStore`（SharedPreferences、`weight_goal_kg`）として実装済みで、`WeightScreen`のグラフにゴールラインとして表示されている。本設計では新規テーブルを作らず、ホーム画面の「今週の目標」から`WeightGoalStore.goal`を直接参照する。

## 5. シード同期の仕組み

- 計画データは `PlanSeeds.kt`（仮称）にコード内リストとして保持する（例: `object PlanSeeds { val goals = listOf(...); val weeklyPlans = listOf(...); val strengthTargets = listOf(...) }`）。
- アプリ起動時（データベース初期化時）に、シードのうちRoomにまだ存在しないレコード（idで判定）だけをinsertする「追記専用」の同期処理を行う。既存レコードの上書き・削除は行わない。
- 「来週の計画を追加する」= このリストに新しいエントリを追記するコード変更、というのがGit更新の実体になる。
- 新規テーブルの追加は既存のRoom migrationパターン（`AppDatabase.kt`、現在version 6）に従い、version 7として追加する。

## 6. 新スキル `/weekly-plan`（仮称）

kaizenスキルの精神（小さく・頻繁に・記録を残しながら、mainは常に安全）をそのまま踏襲し、対象を「機能の不満」から「目標値」に変える。

### なぜこの形か

- kaizenと同じ理由により、**マージだけは人間が判断する**。計画データも「本人が実際に従う目標」として実データ運用されるため、確認なしの自動反映は避ける。
- ブランチ上での試行錯誤は自由。壊れても良い。

### 手順

1. **直近の実績を確認する**: Roomクエリ、または既存のJSONバックアップ（FR-11）から、先週のWeeklyPlanEntity・WeeklyStrengthTargetEntityと実績を突き合わせる。
2. **会話する**: 先週どうだったか、長期目標に対する進捗はどうかを踏まえ、ユーザーと相談しながら来週の数値目標を決める。ここが「AIと一緒に計画を立てる」部分そのもの。
3. **ブランチを切って `PlanSeeds.kt` に追記する**: 命名は `codex/plan-<週開始日>`（例: `codex/plan-2026-09-07`）。
4. **ビルド確認 → PR作成**: ビルドコマンドで確認し、変更内容をまとめてPRを作成する。マージはしない。

## 7. UI変更

### 7.1 ホーム画面

既存の当日サマリー（変更なし）とは別に、「今週の目標」セクションを追加する。

- **長期目標**: GoalEntityの最新1件を、タイトルと期限のテキストで表示（例: 「2027年3月までにハーフマラソン完走」）。該当データが無ければセクション自体を出さない。
- **筋トレ**: 計画◯種目中△種目実施（週内に同名種目の実績が1件でもあれば「実施」とみなす。reps/sets達成は問わない。§8参照）
- **ラン**: 実績◯km／目標△km（`targetRunningKm` に対する週内のRunningEntity距離合計）
- **体重**: 現在値→`WeightGoalStore`の目標との差

対応する計画データが無い週は、各カードを個別に非表示にする（全体を隠すのではなく、ある項目だけ出す）。

### 7.2 筋トレ: 種目ピッカー画面（ExercisePickerScreen）

`ExerciseRow`に、今週の計画にあってまだ実施していない種目には、既存の⭐（よく使う種目マーカー）と同様の位置に目印バッジ（例: 🎯アイコン）を追加する。

### 7.3 筋トレ: セット入力画面（SetInputScreen）

既存の「前回(日付): 60kg×10 / ...」という参考表示と同じ場所に、「今週の目標: 10回×3セット」を追加表示する（該当する週次計画が無ければ表示しない）。あわせて、最初のセット行の「回数」欄の`placeholder`に目標回数を表示する。

### 7.4 ランニング: メイン画面（RunningMainScreen）

タイマーカード付近に、「残り目標: ◯km（目標△km）」のテキストを表示する（該当する週次計画が無ければ表示しない）。

### 7.5 変更なしの画面

食事タブ、体重タブ（既存の目標機能はそのまま）、データ画面、ランニング手入力画面は変更しない。

## 8. 達成状況の計算ロジック（ドメイン層）

新規ファイル（例: `domain/PlanProgress.kt`）に、既存の `Stats.kt` / `StrengthStats.kt` と同様のパターンで実装する。

- **筋トレの実施判定**: 対象週の日付範囲でStrengthEntityをクエリし、`ex` が完全一致するレコードが1件でも存在すれば「実施」とする。reps/setsが目標値以上かどうかは判定に使わず、入力時の目安表示にのみ使う（曖昧な部分判定を避けるため）。
- **ラン達成率**: 対象週のRunningEntityの `dist` 合計を `targetRunningKm` と比較する。
- **体重進捗**: 直近のWeightEntityと`WeightGoalStore.goal`の差を計算する（新規ロジックは薄く、既存の値を読むだけ）。

計画データ（Plan/Goal）と実績データ（既存テーブル）は常にその場で突き合わせて計算し、達成状態を独立して保存しない（二重管理を避けるため）。

## 9. テスト方針

既存の `app/src/test` パターンに合わせ、`PlanProgress` の計算ロジックに対してユニットテストを追加する。少なくとも以下をケースに含める。

- 週境界（週の最初/最後の日の実績が正しく集計されるか）
- 目標未設定の週（該当カードが表示されないこと）
- 筋トレの種目名不一致（実績はあるが計画と種目名が違う場合、未実施として扱われること）

## 10. 非機能要件との整合性

- **外部送信しない**（要件定義書§4）: 維持。AIとの対話はアプリの外で行い、アプリ自体に通信機能は追加しない。
- **オフラインで全機能動作**: 維持。計画データはビルド時にアプリへ同梱される。
- **既存の記録機能・データ構造**: 無改造。

---

## 11. 未確定事項・今後の検討課題

- **週の起算日**: 月曜始まりと仮定している。日曜始まりが良ければ実装時に変更する。
- **セット入力画面のplaceholderの対象**: 「最初のセット行のみ」と仮定している。2セット目以降は前の行の値をコピーする既存動作を優先し、targetのplaceholderは出さない。
- **長期目標が複数ある場合の扱い**: データ上は複数保持できるが、UIは直近1件のみを表示する前提。
- **`/weekly-plan` という名称**: 仮称。実装時に確定する。
- **筋トレの「実施」判定基準**: 種目名の完全一致のみを基準としている。表記ゆれ（全角/半角等）の扱いは、既存の`presetPartOf`と同様、trim程度に留める前提。
